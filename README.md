# CS Virtual Lab — Web Simulator for the BTech Computer Science Curriculum

A browser-based laboratory that lets students **practise the entire Computer Science
degree** without owning expensive hardware. Every practical in the BTech Computer
Science curriculum (Ho Technical University, GTEC-accredited, 2022) becomes an online
simulation with **Beginner, Intermediate and Advanced** labs.

Built for African Computer Science, ICT and Computer Engineering students: works on
low-end laptops and Android phones, on slow or intermittent internet, and runs almost
all computation inside the browser so hosting stays cheap.

## Why

- The source curriculum lists 110 of 260 computer-lab seats as *Bring Your Own Device*.
- Courses such as Basic Electronics, Digital Logic, Computer Hardware, Networking,
  Systems Administration and IoT assume lab kits, routers, servers and boards that
  most students never touch.
- A simulator gives every student unlimited, safe, repeatable practice on their own device.

## Running it

```bash
npm install
```

```bash
npm run dev
```

Then open http://localhost:5173. Every simulation runs in the browser, so this alone is
enough to work through labs and topic checks; progress is kept on the device.

To use accounts in development, also start the API in a second terminal:

```bash
npm run dev:api
```

It listens on http://localhost:8787 with an **embedded Postgres** (PGlite, stored under
`apps/api/.data`), so nothing needs installing. The web dev server proxies `/api` to it.
If the API is not running, the app simply works as a guest.

`npm test` runs the engine, content and API tests (the API tests use an in-memory
Postgres). `npm run typecheck` and `npm run build` cover both the web app and the API.

## Accounts and progress

- **On the device first.** Results, topic mastery and saved circuits are written to the
  browser's storage before anything else, so labs work offline and without an account.
- **Account sync.** With an account (email and password), every result also goes into a
  queue that the app sends to the API when online, in order, in batches. Each item carries a
  client attempt id, so a batch sent twice never duplicates a row. Signing in on another
  device pulls the account's records and merges them with what is on the device by keeping
  the best of each value: a passed lab stays passed, the higher mastery and score win.
- **Progress file.** The profile page can also export everything as a small JSON file and
  import it elsewhere, with the same merge. Useful with no account or no connection. The
  format is `ProgressSnapshot` in [packages/lab-runtime/src/progress.ts](packages/lab-runtime/src/progress.ts).
- **Privacy.** The API stores an email, a scrypt password hash, a display name, a username
  and the learning records above. Learners can delete their account from the profile page.

The API is [apps/api](apps/api): Fastify, `pg` in production, PGlite in development and
tests, migrations in [apps/api/migrations](apps/api/migrations), and the routes in
`apps/api/src/app.ts` (`/api/auth/*`, `/api/me`, `/api/me/profile`, `/api/me/progress`,
`/api/me/progress/sync`). The community and competition schema for later phases is kept
as design reference in `docs/reference/community-and-competition-schema.sql`.

## Research data and privacy

While a learner is signed in, the app records **learning events** in xAPI form (course and
unit views; lab launched, hints, checks and their outcome, resets, a snapshot of the lab work
at each check; topic-check answers right or wrong; consent changes), each with time on task,
device class and connection class. The rules, in short:

- **Pseudonymous from the start.** Events live in a separate `analytics` schema under a
  research id, an HMAC of the account id with a secret (`RESEARCH_SALT`) kept outside the
  database. No email, name, username, account id or IP address enters that schema.
- **Research use is a separate, opt-in choice, off by default**, per purpose (events, lab
  snapshots, social activity counts, follow-up contact) on the profile page, with the notice
  at `/research-data` ([docs/governance/privacy-notice.md](docs/governance/privacy-notice.md)).
  Under-18 learners must confirm guardian or institution agreement. Each event records whether
  research use was consented at the moment it arrived, so withdrawal takes effect at once.
- **Closed vocabulary.** Every event is validated against the platform's xAPI profile
  (`packages/lab-runtime/src/xapiProfile.ts`); unknown verbs, object types or oversized
  payloads are rejected. Free text never enters the research stream.
- **Learners own their data**: the "Your data" page (`/profile/data`) shows what was recorded,
  downloads it as JSON or CSV, and deletes it; deleting the account removes everything except
  records the learner agreed to share for research.
- **Every self-export, re-identifying lookup, deletion and consent change is logged** in
  `analytics.access_log`.
- **Researchers** request access with [docs/governance/data-access-request.md](docs/governance/data-access-request.md)
  and sign [docs/governance/data-use-agreement.md](docs/governance/data-use-agreement.md). The
  release-building export job (re-keying, de-identification, codebook) is the next piece to build.
- **Operational logs** carry method, path, status and timing only, redact auth headers, and are
  rotated by Docker.

The full design (standards: xAPI, FAIR, DDI, Act 843, GDPR, ISO/IEC 29100; tiers; release
process) is [docs/05-LEARNING-ANALYTICS-AND-RESEARCH-DATA.md](docs/05-LEARNING-ANALYTICS-AND-RESEARCH-DATA.md),
and [docs/governance/implementation-status.md](docs/governance/implementation-status.md) says
which parts are built.

## Deploying to a VPS (Hostinger or any Ubuntu server)

One `docker compose` stack runs Postgres, the app (API plus the built web app on the same
origin) and Caddy, which handles HTTPS automatically for a domain.

1. On the VPS, install Docker: `curl -fsSL https://get.docker.com | sh`.
2. Clone this repository and create the server env file:

```bash
git clone <your repository url> cs-virtual-lab && cd cs-virtual-lab && cp .env.example .env
```

3. Edit `.env`: set a long random `POSTGRES_PASSWORD`, and set `DOMAIN` to your domain
   (point its DNS A record at the VPS first). With only an IP for now, use
   `DOMAIN=http://<ip>` so Caddy serves plain HTTP.
4. Start everything:

```bash
docker compose up -d --build
```

The app runs the database migrations itself on start. Open `https://<your domain>`; the
API answers at `/api/health`. To update, `git pull` and run the same command again.
Back up with `docker compose exec db pg_dump -U cslab cslab > backup.sql`.

## Content layout

```
content/courses/<course-slug>/<lab>.json            a lab (optional "unit" and "topicIndex" attach it to a syllabus topic)
content/courses/<course-slug>/checks/<unit>-<topic>.json   a topic check: a pool of items, 5 to 8 drawn per sitting
data/courses.json                                    syllabus units and topics per course (1-based numbering everywhere)
```

Topic check items are `choice` (one answer), `multi` (every right answer and nothing else),
`numeric` (with an optional `tolerance`) and `text` (matched in full against `pattern`).
Grading runs in the browser; the test suite checks that every pool validates and passes with
its own answer key.

## Hosting principles

The platform is a hosted website: students open one address and every simulation runs
inside the page, with nothing to install. The web app and the API are served from the same
origin by our own server, and the database is our own Postgres. No third-party platform
service is used, so the only external dependency is the VPS itself. GitHub Actions
(`.github/workflows/ci.yml`) runs the tests, the type check and the build on every push.
The schema for the later community and competition phases is kept as a reference in
`docs/reference/community-and-competition-schema.sql` and will be ported into
`apps/api/migrations` phase by phase.

## Repository layout

```

apps/api                         Accounts and progress sync API (Fastify, Postgres; PGlite in development)
packages/lab-runtime             Lab spec types, check runner, topic-check grading, mastery rules and the progress format
packages/engine-digital-logic    Digital logic engine: circuit model, evaluation, truth tables, checks, tests
content/courses/<course-slug>/   Lab specs (JSON with Markdown instructions), one file per lab
data/                            Course catalogue, source curriculum, detailed syllabi
scripts/build-courses.mjs        Regenerates data/courses.json
```

## Status

Phase 1 in progress. The platform shell (catalogue, course pages, lab workspace, progress,
offline PWA) and the first flagship simulator, the Digital Logic circuit bench, are built,
with six graded labs for Digital Logic Design. Phase 1b adds accounts with an API of our
own (self-hosted, Docker Compose), offline-first progress sync, a profile page with progress
export and import, syllabus units with a mastery marker per topic, and topic checks, with
real checks for the first three units of Digital Logic Design. Next: the
remaining Phase 1 engines (code runner, network simulator, SQL engine, step visualiser,
maths lab), tutorials, and detailed syllabi for every course.
